# 各信息源查法细则（按信息源展开，正文五问拿不准时读这里）

> 以下为 2026-10 通用做法快照；具体工具随 harness 不同，按"通用性"原则降级或跳过。

## 查"有没有类似轮子"（GitHub）

- 关键词组合搜：功能词 + 场景词（"rust cli table" 比 "table" 好）；中文项目加上语言/框架名
- 排序先看 **star 数 + 最近提交时间**：高星但半年没动 = 慎用；低星但活跃 = 值得关注
- 重点读三处：**README 的设计说明**（它解决了什么问题、不解决什么）→ **issue 里的 bug/坑**（搜 "not work / regression / 回归"）→ **CHANGELOG**（版本踩过的坑）
- 结论形式："有 X 仓库（某 star 数，活跃/停滞），能覆盖需求的哪部分，哪部分仍需自研"
- 拿不准用哪个时：2~3 个候选就够，别海选

## 大工程第二轮：GitHub 特定方面定点搜集

第一轮广泛搜索后，按任务**当场列出 2~4 个特定方面**（别照抄别家清单），每个方面去 GitHub 对应位置定点搜一轮：

- **同领域 awesome 列表**（搜 "awesome + 领域词"）：该领域的轮子和坑的索引
- **同类项目的 issues 区**：搜"我准备做的事/遇到的同类问题"，看别人怎么解决、卡在哪
- **GitHub Search 限定近期**（近 6 个月新建、star 排序）+ **Trending**：领域里新冒出来的方案，最能反映"现在"而不是"我记忆里"
- **相关项目源码**：选定 1~2 个最相关的直接读实现（比博客准）

筛选标准：**只留直接影响"方向/改法决策"的信息**；带时间戳写进侦察结论（"截至 X 月，主流做法是 Y"）。

## 查项目文档

- 找文件顺序：`README*` → `docs/` → `CONTRIBUTING*` → `AGENTS.md` / `CLAUDE.md` / 项目约定文件 → 源码目录里的注释
- **项目内规则优先级最高**：它和你记忆里的"通用做法"冲突时，以它为准（这是用户/维护者写死的约定）
- 文档和代码明显不一致时：读代码确认真实行为，并在侦察结论里指出"文档过时"

## 查用户给的参考

- 回读当前对话里所有 URL、贴的文档、示例代码、口述偏好；没真正读过的先读
- 用户说"参考 X 项目"时，把 X 的**关键部分**（架构、API 设计、约定）读到位再动手，别只扫 README

## 查公开项目源码 / 逆向工具逆向

- 能拿到源码：clone 后直接读（比博客/二手资料准）；重点读入口文件 + 与需求相关的模块
- 只有二进制：用逆向工具（如 IDA / Ghidra 等）逆向；没有可用的逆向工具就跳过这一问并写明"没查"
- 逆向结论标注置信度：反编译出来的字符串/偏移可能误导，关键结论尽量与文档/行为对照

## 查自己代码库

- 相关模块定位：Grep 关键词（函数名/报错信息）→ Glob 找文件 → Read 核心文件
- 历史改动：`git log -- <路径>`、`git log -S <关键词>`（找引入/删除某段代码的 commit）
- 已有测试/注释里的答案：报错信息先全项目搜一遍——经常有人已经在某处踩过并留了注释

## Token 经济（查而不炸）

- 先窄后宽：先查最相关的 1~2 个信息源，不够再扩
- 读大文件用 Grep 定位行段再 Read 局部，别整文件吞
- 侦察结论 5~10 行封顶；用户 token 余量紧时，"查不到"比"查很多"好——写清楚查了什么、没查到什么，直接进方案
